# Standard-material shader feasibility

## Verified

### Runtime VS identity and bank parent

- The retained (not committed) draw-identity record had **64** records for VS `79eac49585797037` + PS `401a01fd4e5f8757`, all from frame 13098/submission 22983. Forty-four are the previously measured 192-index, 16-bit triangle-list form. This is a truncated one-frame sample; the imported catalogue manifest preserves the input hash.
- `79eac49585797037` occurs as a verified XXH3-64 cache entry in the Release XESH at `/mnt/HDD/git_stuff/my_git/Fable-2-Recomp/out/build/linux-amd64-release/cache/shaders/shareable/4D5307F1.xsh`. Its bytecode is 126 dwords, SHA-256 `0e9540f8fc2ac9643d44db8ae879e9064c6b582a3b769b7444ecb1d7b581dbd6`.
- The unique parent under an all-slots fetch-only byte comparison is debug/release bank slot 249 (`VSHADER_STANDARDMATERIAL_BLT1_GLT1_MIST0_AMB2_NRM1` family). Its unpatched microcode XXH3 is `32e39a5c26fe0a63`, SHA-256 `a089b6cb21c9fb049f17160e691351f836c299e45f9ddf1d746358bb91f2b670`.
- The runtime cache code and bank-249 code have equal size. Every changed dword is within five three-dword vertex-fetch instructions (instruction indices 5–9); all other dwords are identical. Changed dword positions are 15–17, 19–20, 22–23 and 25–29. Exact before/after triplets and the unique all-bank fetch-only parent check are in `research/native_reference/standard-material-1d-result.json`. This verifies the proposed bank ancestry at byte level and explains why the runtime XXH3 differs: declaration/fetch patching changes the VS microcode before it is cached. The retained draw record observes vertex fetch slots 94/95, most commonly in 44/64 matching-pair records.
- PS `401a01fd4e5f8757` is an exact raw-microcode match for slot 343; its bytes are SHA-256 `e13407365e53659c9d7e1db2babc7d3c3a98ad1938ecab0c3b53b40b2bcaf87d`. Slot 343 reflects sampler constants `g_InScattering` at register 4 and `g_Extinction` at register 5, and emitted HLSL contains two 1D fetch calls.

### 1D conversion defect and isolated correction

- Pinned XenosRecomp’s fetch translator recognizes `TextureDimension::Texture1D` and emits `tfetch1D` (`upstream/xenosrecomp/XenosRecomp/shader_recompiler.cpp:304-335`). However, its `TEXTURE_DIMENSIONS` declaration list at lines 121–126 only includes 2D, 3D and Cube, so sampler constant generation omits each `_Texture1DDescriptorIndex`. The common shader header also had no `Texture1D` descriptor heap or `tfetch1D` helper. The prior DXC error was therefore an incomplete converter binding/helper path, not a malformed shader container or SPIR-V validator problem. Upstream’s own README says 1D texture support is not implemented.
- Added a **local, reproducible patch** in the isolated converter build, leaving the pinned upstream `.cpp` and `shader_common.h` byte-for-byte unchanged. `apply_1d_patch.py` hash-checks the pinned input and emits a patched copy only under the new build directory. It generates a 1D descriptor index for each reflected sampler and adds a Texture1D heap, sample helper and 1D weight helper.
- The PoC keeps existing binding offsets unchanged (2D 0, 3D 64, Cube 128, sampler 192). The new descriptor-index lane is explicitly an **extension** at SharedConstants byte offset 288 / HLSL `c18`–`c21`; for this pair the 1D indices load at offsets 304 (`g_InScattering`, sampler register 4) and 308 (`g_Extinction`, register 5). Its texture heap uses Vulkan descriptor set 5. The first PoC version put the 1D heap in set 3 and collided with the existing sampler binding at set 3/binding 0. SPIRV-Tools accepted that module, but an explicit binding-uniqueness check caught it. The corrected version uses set 5 and records unique set/binding pairs in `result.json`. Version-one artifacts remain in `standard-material-1d-poc/`; v2 is the first corrected compile, and use `standard-material-1d-poc-v3/` for final parent verification/results.

## Assumptions and remaining semantic risks

- A successful HLSL compile and SPIR-V validation establish syntactic/structural validity, **not** equivalence to Xenos texture behavior. The PoC’s `tfetch1D` currently uses `Texture1D.Sample` (implicit LOD); Xenos computed/register LOD, sampler filtering, bias/offset and other fetch details were not validated against the runtime or a captured output. The added `getWeights1D` helper was not exercised by a retained 1D-weights fixture.
- The 1D descriptor offset and set 5 are a documented isolated shader ABI proposal, not an existing ReXGlue runtime contract. No runtime code currently populates the new SharedConstants lane or binds set 5. Thus this pair is compile-ready in the standalone converter experiment, not yet drop-in usable by a renderer.
- The VS parent relation is exact for the 64-dword capture group tested, but the reconstructed shader does not establish a complete vertex declaration/resource binding contract across all draws or scenes.

## Do we have a credible native shader pair?

**Yes—as a shader-code candidate, not as a complete native draw.** Both exact observed stage identities now have validated SPIR-V, and the runtime VS is byte-verified as a fetch-patched bank-249 variant. The original bank pair names are useful family labels but not proof of all material permutation choices. The actual runtime code was compiled for the VS; the runtime PS is exact bank microcode.

Still required for a complete native draw fixture: raw vertex and index payloads plus the exact declaration/endian/stride interpretation; current per-draw vertex fetch descriptor/buffer contents and resource generations; full VS/PS constant data; bound 1D/2D/etc texture descriptors, sampler state and texture/mip bytes; viewport/scissor, EDRAM/RT/depth formats and contents, blend/depth/stencil/raster state; and a runtime implementation/population rule for the proposed 1D descriptor lane/set. The current metadata capture does not provide those payloads, and the retained `good-guest.rdc` is not proven to contain this same town-square draw/pair.

## Scope and safety

All work ran on the desktop in `research/native_reference` and `research/native_shader_catalogue`. No game launch, Deck deployment, full-game build, RenderDoc investigation, production/game source edit or renderer edit occurred. The pinned upstream converter source and pre-existing survey fixtures remain hash-verified and unchanged. The only code change is confined to the isolated research converter/PoC harness and its new tests.
